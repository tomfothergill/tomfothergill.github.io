Building a frontend without frontend experience

How I use AI tools to build, design and test the frontend of an application I built myself.

I’ve built the frontend for an application at work without writing any of the frontend code by hand. I had no experience in frontend development when I started, although I’ve discovered that this hasn’t prevented me from developing opinions about where things should go. With Claude Code and Codex doing the implementation, I’ve been able to spend much more time using the application, deciding what feels awkward and asking for changes. That has become a substantial part of how I build software.

The application is an analytics agent: someone asks a question about their business data, and it investigates and returns an answer. I work primarily with retail companies, so the question might concern falling sales, differences between stores or which products customers tend to buy together. The application needs to retrieve the relevant data, work through the analysis and explain what it has found. The frontend is everything the person asking the question sees in their browser, including the conversation, charts, tables and ways of looking more closely at the results.

I’m the sole developer on the application, so my work covers the agent itself, the backend, cloud infrastructure and frontend. I’ve built it with AI’s help throughout, but the frontend has involved the most unfamiliar territory. Over time, I’ve settled into a process that lets me work through it in stages, starting with something functional and then spending time on its design.

While I’m building a feature in the backend, I ask Claude Code or Codex to build the interface for it as well. I keep both parts in the same repository, so the tool has access to the code on either side. At this point, I want to be able to submit a question, see the investigation progressing and inspect the answer. Getting that working gives me something concrete to use while I continue developing the underlying behaviour.

Once the feature is working, I take it into Claude Design to explore the layout. We have a company design system set up there, containing our fonts, colours, logos and other assets, so I already have a framework to work within. I’ll go back and forth on the page and its components, asking for alternatives and working out which arrangement makes the most sense. I often find it easier to explain what I want after seeing a version of what I don’t.

For this application, the design needs to accommodate quite different answers. One question might merit a short explanation, while another needs a detailed breakdown with a table or a way to inspect the database query. While an investigation is running, the interface also needs to show enough of the activity to make its progress understandable. Those are the kinds of details I work through in Claude Design: what needs to be visible, what can be opened when useful, and how it should fit together on different screen sizes.

When I’m happy with a design, I use Claude Design’s handoff feature to package it up and bring it back into Claude Code. I’ve found that it reproduces the design very closely, which makes the process pleasantly straightforward. I can spend time getting the layout right, have it applied to the application, then try it with actual responses and make further adjustments.

Alongside that, I’ve built up a suite of end-to-end tests using Playwright. These run the application in a browser and check interactions such as submitting a question, opening a table or returning to an earlier conversation. Most use fixtures: prepared responses that let me test the interface without making a live model call each time. The checks run automatically as part of the deployment process, helping me catch things I’ve broken while concentrating on something else.

That is broadly how I work now: build a functional version alongside the backend, work through the design, bring it back into the application and test it. I still spend plenty of time looking at the result and changing my mind. Being able to get those changes implemented quickly makes that an enjoyable part of the process, and has allowed me to build and maintain a part of the application I would previously have needed considerable help with.
